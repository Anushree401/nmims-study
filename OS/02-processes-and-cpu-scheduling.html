1. In-Depth Theory & Lecture Explanation

Faithful to Unit 2 Slides & NMIMS Past Papers

1.1 The Process Concept & Memory Layout in RAM

In modern computing, the fundamental unit of work is the process.

Formal Definition: Program vs. Process

A Program is a passive entity—a compiled executable file containing machine instructions stored persistently on secondary disk storage (e.g., /bin/ls or a.out).
A Process is an active entity—a program in execution. It encompasses the active machine instructions, current program counter value, processor registers, allocated memory segments, and open file descriptors.

The Four Logical Memory Segments of an Executing Process:

Figure 2.1: Virtual Address Space Memory Layout of a Process.

  • 1. Text Segment: Contains the executable machine code instructions. It is typically marked Read-Only by the MMU to prevent accidental or malicious self-modification, and is shareable among concurrent instances of the same program (e.g., multiple text editors running simultaneously).
  • 2. Data Segment: Contains global and static variables initialized before execution begins, as well as the uninitialized data segment (historically termed BSS - Block Started by Symbol).
  • 3. Heap: Dynamically allocated memory requested by the program at runtime (via malloc() in C or new in C++ / Java). The heap expands upward toward higher memory addresses.
  • 4. Stack: Contains temporary execution context, including local variables declared inside functions, parameter arguments passed into function calls, and saved return addresses. The stack expands downward toward lower memory addresses. If the stack and heap collide due to unbounded recursion or massive allocations, a Stack Overflow error occurs.

1.2 The Process Control Block (PCB): Structure & Significance

Every process in the operating system is represented by an essential kernel data structure called the Process Control Block (PCB) (also known as a Task Control Block or task_struct in the Linux kernel).

Figure 2.2: Detailed internal fields of the Process Control Block (PCB).

Significance of PCB in Enabling Multi-Tasking (Frequent Exam Question):

The PCB is the absolute bedrock of multitasking. Because CPU registers are a single physical set of hardware circuits, they can only hold one process's execution data at any given millisecond. When the operating system preempts Process A to run Process B, the kernel performs a snapshot: it copies the complete hardware CPU register state (Program Counter, Stack Pointer, general-purpose registers) into Process A's PCB in memory. Later, when Process A is rescheduled, the OS reloads the physical CPU registers directly from Process A's PCB. To Process A, execution resumes completely seamlessly as if no interruption ever occurred.

1.3 Process Lifecycle & State Transition Models

As a process executes, it transitions through distinct operating states reflecting its immediate relationship with the CPU and I/O subsystems.

1. The Canonical 5-State Process Model:

Figure 2.3: The Canonical 5-State Process Transition Model.

  • New: The process is currently being created (allocating memory structures and assigning PID), but is not yet loaded into the pool of ready processes.
  • Ready: The process is loaded in main memory and possesses all resources required to execute, waiting exclusively to be assigned a CPU core by the short-term scheduler.
  • Running: Instructions are currently being fetched and executed on the physical CPU core. (On a uniprocessor system, exactly one process can be in this state at any instant).
  • Waiting (Blocked): The process cannot execute even if the CPU were completely idle, because it is actively waiting for an external event to complete (e.g., waiting for disk sectors to read, keyboard input, or a child process to terminate).
  • Terminated (Exit): The process has finished executing its instructions (or was terminated due to a fatal segmentation fault). Its PCB remains temporarily in the process table so the parent can read its exit status code (preventing a Zombie state).

2. The 7-State Model (Swapping & Suspended States - Stallings):

When physical main memory becomes severely overcommitted, the operating system must swap entire dormant processes out of RAM onto secondary disk storage. This introduces two crucial suspended states:

  • Ready / Suspend: The process is in secondary storage (disk swap space), but is immediately ready to execute as soon as it is brought back into main memory.
  • Blocked / Suspend: The process is in secondary storage and is also waiting for an external I/O event to occur. When its I/O finishes, it transitions to Ready / Suspend.

1.4 Context Switching Mechanics & System Overhead

A Context Switch is the low-level mechanism whereby the operating system halts execution of the currently running process and restores the execution state of another ready process onto the CPU.

Figure 2.4: Context switch sequence between Process 1 and Process 2 showing CPU idle overhead.

Exam Crucial Point: Context Switching is Pure Overhead!

During a context switch, the CPU is executing internal kernel dispatch code rather than user applications. No useful application computation is performed. Typical context switch durations range from 1 to 10 microseconds. Furthermore, context switching flushes the CPU's high-speed hardware cache (L1/L2) and invalidates Translation Lookaside Buffer (TLB) entries, degrading execution performance for several thousand cycles immediately after the switch.

1.5 The Three Schedulers: Long-Term, Short-Term & Medium-Term

A classic exam question asks to differentiate between the three structural schedulers:

Scheduler Metric Long-Term Scheduler (Job Scheduler) Short-Term Scheduler (CPU Scheduler) Medium-Term Scheduler (Swapper)
Primary Function Selects candidate jobs from disk pool and admits them into main memory (Ready queue). Selects a process from the Ready queue and assigns it to an active CPU core. Temporarily removes processes from RAM to disk swap space, and returns them later.
Execution Frequency Infrequent (seconds, minutes, or triggered only upon job arrival/exit). Extremely Frequent (invoked every 10 to 100 milliseconds). Intermediate (triggered upon memory pressure or thrashing).
Control Over Multiprogramming Directly controls the Degree of Multiprogramming (number of jobs in RAM). No direct control over the total number of processes in memory. Dynamically reduces or increases the Degree of Multiprogramming.
Speed Requirement Can afford to be relatively slow and deliberative. Must be blindingly fast to minimize scheduling overhead. Moderately fast (dominated by disk I/O seek and transfer times).
System Presence Absent in modern desktop systems; ubiquitous in high-performance batch supercomputers. Mandatory in all modern operating systems. Present in all virtual memory systems supporting swapping.

1.6 Threads, Multithreading & Architecture Models

A Thread (often termed a Lightweight Process - LWP) is the basic unit of CPU utilization.

Process vs. Thread (The Fundamental Boundary):

A Process defines a resource ownership boundary (it owns a dedicated virtual address space, file descriptor table, and security tokens).
A Thread defines an execution dispatch boundary. Multiple threads belonging to the same process share that process's virtual address space (Code, Data, Heap) and open files, but each individual thread maintains its own private:
(1) Unique Thread ID (TID), (2) Program Counter (PC), (3) CPU Register Set, and (4) Private Call Stack.

User-Level Threads (ULT) vs. Kernel-Level Threads (KLT):

Comparison Dimension User-Level Threads (ULT) Kernel-Level Threads (KLT)
Management Layer Managed entirely in user space by a thread runtime library (e.g., POSIX pthreads, green threads). Managed directly by the operating system kernel.
Kernel Awareness Kernel is completely unaware of their existence; sees only one single-threaded process. Kernel maintains a Thread Control Block (TCB) for every individual thread.
Context Switch Speed Extremely fast. Switching between threads requires no supervisor mode traps or mode bit flips. Slower. Switching requires crossing user-kernel protection rings and saving kernel registers.
Blocking I/O Vulnerability Severe Flaw: If one user thread executes a blocking system call, the entire process and all sibling threads are blocked! Resilient: If one thread blocks on I/O, the kernel scheduler immediately dispatches another sibling thread.
Multiprocessor Parallelism Cannot run in parallel across multiple CPU cores; restricted to a single core. True Parallelism: The kernel can schedule different threads of the same process onto different physical CPU cores simultaneously.

The Three Multithreading Architecture Models:

  • 1. Many-to-One Model: Maps many user-level threads to a single kernel thread. Thread management is efficient in user space, but the entire process blocks if a thread makes a blocking call, and multi-core parallelism is impossible.
  • 2. One-to-One Model (Modern Linux & Windows Standard): Maps each user thread to a dedicated kernel thread. Provides true multi-core concurrency; if one thread blocks, others continue. Disadvantage: Creating too many threads creates kernel memory and context-switching overhead.
  • 3. Many-to-Many Model: Multiplexes many user-level threads onto a smaller or equal number of kernel threads. Developers can create hundreds of user threads without flooding the kernel, while still achieving multi-core parallel dispatch.

1.7 CPU Scheduling Algorithms & Decision Criteria

CPU scheduling decisions occur under four distinct operating circumstances:

  1. When a process switches from the Running state to the Waiting state (e.g., I/O request or wait()).
  2. When a process switches from the Running state to the Ready state (e.g., hardware timer interrupt).
  3. When a process switches from the Waiting state to the Ready state (e.g., I/O completion).
  4. When a process terminates.

Under circumstances 1 and 4, there is no choice—the CPU must schedule another process. This is Non-Preemptive (Cooperative) Scheduling. Under circumstances 2 and 3, the OS can choose whether to preempt the running process. This is Preemptive Scheduling.

Core Quantitative Scheduling Metrics:

  • Turnaround Time (\(TAT\)): Total elapsed time from process arrival to final completion: $$\mathbf{TAT = \text{Completion Time } (CT) - \text{Arrival Time } (AT)}$$
  • Waiting Time (\(WT\)): Total time spent sitting idle in the Ready queue waiting for CPU dispatch: $$\mathbf{WT = \text{Turnaround Time } (TAT) - \text{Burst Time } (BT)}$$
  • Response Time (\(RT\)): Elapsed time from submission/arrival until the very first time the CPU begins executing the process: $$\mathbf{RT = \text{First CPU Start Time} - \text{Arrival Time } (AT)}$$

1.8 Multilevel Queue and Multilevel Feedback Queue Scheduling

Multilevel Queue (MLQ) assigns processes to fixed queues by class (for example, interactive and batch). Each queue may use its own policy, while a separate rule selects between queues. A process normally remains in its assigned queue.

Multilevel Feedback Queue (MLFQ) allows processes to move between queues. Short CPU bursts can remain at higher priority; CPU-heavy processes may be demoted, while aging or feedback can promote waiting processes to reduce starvation. The exact number of queues, time quanta, and promotion/demotion rules are policy choices.

FeatureMLQMLFQ
Queue assignmentUsually fixed by process classChanges based on observed behavior or waiting
AdaptivityLowHigher
Key trade-offSimple separation, but rigidResponsive, but needs careful tuning

2. In-Depth Numerical Explanations (Step-by-Step)

Gantt Charts & Detailed Schedule Calculations
Core Problem Type

Problem 2.1: Non-Preemptive Scheduling: FCFS vs. SJF with Equal Arrival

Problem Statement: Consider four processes arriving at time \(t = 0\) with the following CPU burst requirements:
\(P_1: 24\text{ ms}, \quad P_2: 3\text{ ms}, \quad P_3: 3\text{ ms}, \quad P_4: 6\text{ ms}\).
(a) Construct the Gantt chart and compute Average Waiting Time under First-Come, First-Served (FCFS) (assuming arrival order \(P_1, P_2, P_3, P_4\)).
(b) Construct the Gantt chart and compute Average Waiting Time under Shortest Job First (SJF) non-preemptive.
(c) Explain the Convoy Effect observed in part (a).

PART (a) FCFS

Gantt Chart (FCFS):

|      P1 (24)      |  P2 (3)  |  P3 (3)  |   P4 (6)   |
0                  24         27         30           36

Calculations:

  • \(WT(P_1) = 0 - 0 = 0\text{ ms}\)
  • \(WT(P_2) = 24 - 0 = 24\text{ ms}\)
  • \(WT(P_3) = 27 - 0 = 27\text{ ms}\)
  • \(WT(P_4) = 30 - 0 = 30\text{ ms}\)
$$\text{Average Waiting Time (FCFS)} = \frac{0 + 24 + 27 + 30}{4} = \frac{81}{4} = \mathbf{20.25\text{ ms}}$$
PART (b) SJF

SJF Execution Order: Shortest bursts first: \(P_2 (3\text{ ms}) \to P_3 (3\text{ ms}) \to P_4 (6\text{ ms}) \to P_1 (24\text{ ms})\).

Gantt Chart (SJF Non-Preemptive):

|  P2 (3)  |  P3 (3)  |   P4 (6)   |          P1 (24)         |
0         3          6            12                         36

Calculations:

  • \(WT(P_2) = 0 - 0 = 0\text{ ms}\)
  • \(WT(P_3) = 3 - 0 = 3\text{ ms}\)
  • \(WT(P_4) = 6 - 0 = 6\text{ ms}\)
  • \(WT(P_1) = 12 - 0 = 12\text{ ms}\)
$$\text{Average Waiting Time (SJF)} = \frac{0 + 3 + 6 + 12}{4} = \frac{21}{4} = \mathbf{5.25\text{ ms}}$$
THE CONVOY EFFECT

FCFS Avg WT = \(\mathbf{20.25\text{ ms}}\) vs. SJF Avg WT = \(\mathbf{5.25\text{ ms}}\) (3.85× reduction!)

Convoy Effect Explained: Under FCFS, when a massive CPU-bound job (\(P_1\)) executes first, all short I/O-bound jobs (\(P_2, P_3, P_4\)) are forced to wait in a long "convoy" behind it. Their I/O devices sit completely idle during this period, severely lowering overall system device and CPU throughput.

Problem 2.2: Shortest Remaining Time First (SRTF Preemptive) with Staggered Arrivals

Problem Statement (NMIMS Exam Classic): Consider four processes arriving at varying arrival times with CPU burst requirements as follows:

ProcessArrival Time (\(AT\))Burst Time (\(BT\))
\(P_1\)08
\(P_2\)14
\(P_3\)29
\(P_4\)35

Draw the execution Gantt chart under SRTF (Preemptive SJF), calculate Completion Time (\(CT\)), Turnaround Time (\(TAT\)), and Waiting Time (\(WT\)) for each process, and find the Average Waiting Time.

TRACE LOGIC

Step-by-Step Scheduling Decisions:

  • At \(t = 0\): Only \(P_1\) is present (Remaining: 8). \(P_1\) starts running.
  • At \(t = 1\): \(P_2\) arrives with \(BT = 4\). \(P_1\) has remaining burst \(8 - 1 = 7\). Since \(4 < 7\), \(P_2\) preempts \(P_1\)!
  • At \(t = 2\): \(P_3\) arrives (\(BT = 9\)). \(P_2\) remaining is 3. \(P_2\) continues.
  • At \(t = 3\): \(P_4\) arrives (\(BT = 5\)). \(P_2\) remaining is 2. \(P_2\) continues.
  • At \(t = 5\): \(P_2\) completes (\(CT = 5\)). Ready queue has: \(P_1\) (rem 7), \(P_3\) (rem 9), \(P_4\) (rem 5). Shortest is \(P_4\). \(P_4\) runs for 5 units until \(t = 10\).
  • At \(t = 10\): \(P_4\) completes (\(CT = 10\)). Ready queue has: \(P_1\) (rem 7), \(P_3\) (rem 9). Shortest is \(P_1\). \(P_1\) runs for 7 units until \(t = 17\).
  • At \(t = 17\): \(P_1\) completes (\(CT = 17\)). \(P_3\) runs for 9 units until \(t = 26\).

Gantt Chart (SRTF):

|  P1  |     P2 (4)     |     P4 (5)     |        P1 (7)       |          P3 (9)         |
0      1                5               10                   17                          26
METRIC TABLE
ProcessArrival (\(AT\))Burst (\(BT\))Completion (\(CT\))\(TAT = CT - AT\)\(WT = TAT - BT\)
\(P_1\)0817\(17 - 0 = 17\)\(17 - 8 = 9\)
\(P_2\)145\(5 - 1 = 4\)\(4 - 4 = 0\)
\(P_3\)2926\(26 - 2 = 24\)\(24 - 9 = 15\)
\(P_4\)3510\(10 - 3 = 7\)\(7 - 5 = 2\)
AVERAGES

$$\text{Average Turnaround Time} = \frac{17 + 4 + 24 + 7}{4} = \frac{52}{4} = \mathbf{13.00\text{ ms}}$$ $$\text{Average Waiting Time} = \frac{9 + 0 + 15 + 2}{4} = \frac{26}{4} = \mathbf{6.50\text{ ms}}$$

Sanity Check: Average \(WT\) must equal Average \(TAT\) minus Average \(BT\). Here, Average \(BT = (8 + 4 + 9 + 5)/4 = 6.50\), so \(13.00 - 6.50 = 6.50\) ms. Verified!

Challenging Multi-Round Type

Problem 2.3: Round Robin (RR) with Time Quantum \(q = 2\)

Problem Statement: Consider three processes arriving at \(t = 0\) with burst times: \(P_1 = 5\text{ ms}, P_2 = 3\text{ ms}, P_3 = 1\text{ ms}\).
Using Round Robin scheduling with time quantum \(q = 2\text{ ms}\), construct the Gantt chart, trace the Ready queue after each slice, and compute average waiting time.

QUEUE TRACE

Step-by-Step Ready Queue Tracking:

  • Initial Queue at \(t = 0\): \([P_1, P_2, P_3]\).
  • \(P_1\) executes for \(\min(5, 2) = 2\) units \(\to t = 2\). Remaining \(P_1 = 3\). Queue becomes: \([P_2, P_3, P_1]\).
  • \(P_2\) executes for \(\min(3, 2) = 2\) units \(\to t = 4\). Remaining \(P_2 = 1\). Queue becomes: \([P_3, P_1, P_2]\).
  • \(P_3\) executes for \(\min(1, 2) = 1\) unit \(\to t = 5\). \(P_3\) finishes (\(CT = 5\)). Queue becomes: \([P_1, P_2]\).
  • \(P_1\) executes for \(\min(3, 2) = 2\) units \(\to t = 7\). Remaining \(P_1 = 1\). Queue becomes: \([P_2, P_1]\).
  • \(P_2\) executes for \(\min(1, 2) = 1\) unit \(\to t = 8\). \(P_2\) finishes (\(CT = 8\)). Queue becomes: \([P_1]\).
  • \(P_1\) executes for remaining 1 unit \(\to t = 9\). \(P_1\) finishes (\(CT = 9\)).

Gantt Chart (RR, \(q = 2\)):

|  P1 (2)  |  P2 (2)  | P3 (1) |  P1 (2)  | P2 (1) | P1 (1) |
0          2          4        5          7        8        9
METRICS
  • \(TAT(P_1) = 9 - 0 = 9 \implies WT(P_1) = 9 - 5 = 4\text{ ms}\)
  • \(TAT(P_2) = 8 - 0 = 8 \implies WT(P_2) = 8 - 3 = 5\text{ ms}\)
  • \(TAT(P_3) = 5 - 0 = 5 \implies WT(P_3) = 5 - 1 = 4\text{ ms}\)
$$\text{Average Waiting Time} = \frac{4 + 5 + 4}{3} = \frac{13}{3} \approx \mathbf{4.33\text{ ms}}$$

4. Real-World OS Schedulers

Production Implementations
Production Kernel Case Study

The Linux Completely Fair Scheduler (CFS)

Modern Linux servers do not use simple textbook Round Robin. Since kernel version 2.6.23, Linux defaults to the Completely Fair Scheduler (CFS):

  • Virtual Runtime (vruntime): CFS tracks the exact nanoseconds of CPU execution awarded to every process. To maintain fairness, CFS always selects the process that has received the least virtual runtime.
  • Red-Black Tree (\(O(\log N)\)): Instead of linear ready queues, runnable tasks are ordered in a time-balanced Red-Black Tree. The leftmost node has the smallest vruntime and is dispatched in \(O(1)\) time.
  • Nice Levels: Process priority (-20 to +19) weights how fast vruntime accumulates. High priority jobs accumulate vruntime slowly, allowing them more CPU bursts before being preempted.

10 Marks

Q3. What is starvation in CPU scheduling? Which algorithms suffer from it, and what technique is used to prevent it? [From NMIMS Past Papers]

Official Marking Scheme:

  • Definition of Starvation (Indefinite Blocking): 2 Marks
  • Identification of vulnerable algorithms (SJF, SRTF, Priority): 3 Marks
  • Detailed explanation of the Aging technique with numerical example: 5 Marks

Model Answer Key: Define starvation as the condition where a runnable process waits indefinitely in the Ready queue because higher-priority or shorter jobs continuously arrive. It occurs in SJF, SRTF, and Priority. The standard solution is Aging—gradually incrementing the priority integer of a process as it spends time waiting in the Ready queue (e.g., increase priority by 1 every 15 minutes of wait time). Eventually, even the lowest priority job becomes the highest priority job in the system and is guaranteed CPU dispatch.

Final Revision Anchor

Core Exam Takeaways:

  • Memory Layout: Stack grows down; Heap grows up; Text is read-only.
  • PCB is King: Multitasking is physically impossible without PCB state saving.
