1. The machine an OS manages

A computer combines a processor (executes instructions), main memory (fast, volatile working storage), I/O modules/devices, persistent storage, and a system bus. The OS coordinates these shared resources so applications can run safely and usefully.

User / application → system-call interface → kernel → CPU, memory, devices, storage

The OS is both a resource manager and an interface. Convenience, efficiency, and the ability to evolve are its stated objectives.

2. Core responsibilities and quality goals

Process management
Track process state, schedule CPU time, allocate and release processor resources.
Memory management
Decide which processes occupy main memory, allocate regions, and reclaim them.
I/O management
Track devices, arbitrate access, and allocate/deallocate devices.
Protection and security
Protect resources and data. Availability resists interruption; confidentiality limits unauthorized reading; integrity prevents unauthorized changes; authenticity verifies identity or message validity.
Scheduling goals
Balance fairness, differential responsiveness for different job classes, and efficiency (throughput, response time, user capacity).

3. Kernel, shell, system calls

The kernel is the privileged core that manages hardware resources and implements OS services. A shell is a user-facing command interpreter/interface to kernel services. Programs request protected operations through system calls, commonly exposed through language libraries; categories include process control, memory, files/directories, devices, protection, and networking.

Do not conflate a shell command with the system call itself: a shell parses user commands; a program/library invokes the kernel interface.

4. Evolution and operating-system organization

Serial processing ran jobs one at a time with little automation. Batch systems queue submitted jobs and execute them without interactive input; long jobs can delay later work. Multiprogramming keeps several jobs resident and switches CPU work while one waits for I/O. Multitasking/time sharing gives jobs/users short turns for interactive response. Multiprocessing uses multiple processors for true parallel execution and higher throughput.

A monolithic design puts many services in one kernel address space: direct interaction can be fast, but changes and faults can affect a large tightly coupled core. A layered design organizes services into levels: modularity and localized debugging improve, while boundaries/layout add complexity and can make cross-layer work slower.

Common confusions and exam traps

Multiprogramming overlaps CPU and I/O across jobs; multiprocessing has multiple processors; multitasking is the user-visible time-sharing behavior. Main memory is volatile; disk storage persists. Efficiency is not the only OS objective. “Shell translates high-level language to low-level” is imprecise in the slides: learn it as command interpreter/interface, not as a compiler.

Recap and self-test

Self-test (answers follow)

What are the three stated OS objectives?

Convenience, efficient resource use, and ability to evolve.

How do multiprogramming and multiprocessing differ?

Multiprogramming overlaps jobs on a processor, often using CPU while another job waits for I/O. Multiprocessing provides multiple processors that can execute in parallel.

Give four protection/security goals listed in the slides.

Availability, confidentiality, integrity, and authenticity.

Why use system calls?

They provide the controlled interface through which programs request OS services.

What to know for the exam

Be ready to define the central terms, compare mechanisms using their assumptions and trade-offs, trace a process or algorithm step by step, and justify the result. State units and conventions whenever a question supplies them.
