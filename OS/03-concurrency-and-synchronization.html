1. Why concurrency is difficult

Concurrent processes/threads make progress in overlapping time. Multiprogramming interleaves jobs on one CPU; multiprocessing allows simultaneous execution on multiple processors; distributed processing spans machines. Shared state makes results depend on timing. A race condition occurs when the outcome depends on the order of unsynchronized reads/writes.

Example: two threads both execute x=x+1. Each may read x=0, compute 1, and store 1; the intended result 2 is lost. The operation is a read-modify-write sequence, not inherently atomic.

2. Critical-section requirements

A critical section accesses shared state. A correct entry protocol requires mutual exclusion (only one at a time), progress (selection cannot be postponed by processes outside the section), and bounded waiting (a requester cannot be bypassed forever). Also avoid assuming relative speeds, keep sections finite, and ensure a process halted outside the section does not block others.

3. Mechanisms

Mutex lock: acquire before critical work, release after; a busy-wait spin lock wastes CPU while waiting, so use only when waiting is expected to be brief or blocking is unavailable. Hardware atomic instructions such as test-and-set and compare-and-swap provide indivisible lock acquisition. Peterson’s solution demonstrates software coordination for two processes using intent flags and a turn variable; it relies on assumptions about atomic reads/writes and is primarily conceptual.

Semaphore: integer plus possible waiting queue. wait/down/P atomically decrements or blocks; signal/up/V atomically increments and may wake a waiter. A binary semaphore has 0/1 state; a counting semaphore represents multiple identical resources. Initialize a resource semaphore to capacity N. Keep wait/signal ordering balanced.

Monitor: high-level construct encapsulating shared data and procedures; only one process is active inside at a time. Condition variables provide wait/signal for a condition. Signal-and-continue versus signal-and-wait semantics differ: state which convention applies when tracing.

Message passing: send/receive primitives exchange information and coordinate processes without shared variables; communication may be direct/indirect and blocking/nonblocking depending on system.

4. Classical patterns and traps

  • Producer–consumer: bounded buffer; use mutex for buffer integrity, empty count initialized to capacity, full count initialized to zero. Producer waits(empty), locks, inserts, unlocks, signals(full); consumer waits(full), locks, removes, unlocks, signals(empty).
  • Readers–writers: multiple readers may share; writers need exclusive access. Reader preference can starve writers; writer preference can starve readers.
  • Dining philosophers: competing for two adjacent forks; naive simultaneous pickup can create circular wait. Break a condition (e.g. impose order, limit entrants, or use a monitor).

Common trap: acquire mutex before waiting for a resource count can deadlock the consumer/producer. Resource-count waits usually precede mutex acquisition; release the mutex before signaling availability.

Recap and self-test

Self-test (answers follow)

Name the three core critical-section properties.

Mutual exclusion, progress, and bounded waiting.

What does wait(P) do?

Atomically decrements a semaphore if possible; otherwise blocks until it can proceed.

Why is x=x+1 unsafe when shared?

It is a multi-step read-modify-write and concurrent interleavings can lose an update.

Producer–consumer semaphore initialization for buffer capacity N?

empty=N, full=0, mutex=1 (binary).

Why can readers–writers policy starve one side?

Preference rules may continually admit one class ahead of the other.

What to know for the exam

Be ready to define the central terms, compare mechanisms using their assumptions and trade-offs, trace a process or algorithm step by step, and justify the result. State units and conventions whenever a question supplies them.
