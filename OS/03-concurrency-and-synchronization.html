1.1 Race Conditions & The Anatomy of Concurrent Bugs

When multiple concurrent processes execute and access shared mutable data (such as a shared variable, memory buffer, or file), the outcome of execution depends strictly on the unpredictable order in which individual machine instructions are interleaved by the CPU scheduler. This catastrophic flaw is called a Race Condition.

Classic Concrete Example: The Shared Counter

Suppose two processes \(P_1\) and \(P_2\) share integer variable count = 5. Both concurrently execute count++ and count--:

// In Process 1: count++           // In Process 2: count--
register1 = count;                register2 = count;
register1 = register1 + 1;        register2 = register2 - 1;
count = register1;                count = register2;

If the CPU timer interrupt causes an arbitrary context switch between machine instructions:

  1. \(P_1\) loads register1 = count (\(\text{reg}_1 = 5\)).
  2. \(P_1\) increments register1 = register1 + 1 (\(\text{reg}_1 = 6\)).
  3. Context switch to \(P_2\) occurs before \(P_1\) writes back!
  4. \(P_2\) loads register2 = count (\(\text{reg}_2 = 5\)).
  5. \(P_2\) decrements register2 = register2 - 1 (\(\text{reg}_2 = 4\)).
  6. \(P_2\) writes count = register2 (\(\mathbf{\text{count} = 4}\)).
  7. Context switch back to \(P_1\)!
  8. \(P_1\) finishes its instruction: writes count = register1 (\(\mathbf{\text{count} = 6}\)).

The Catastrophe: After one increment and one decrement, count should be 5. Instead, it is 6 (or 4 if interleaved oppositely)! The write from \(P_2\) was completely obliterated. To prevent this, operations on shared data must be executed with Atomicity (as an indivisible, uninterrupted unit).

1.2 The Critical Section Problem & Its Three Axioms

Any program running concurrent cooperating processes is structurally divided into four regions:

Figure 3.1: Structural decomposition of a concurrent process into Entry, Critical, Exit, and Remainder sections.

The Three Mandatory Requirements of any Critical Section Solution:

  1. 1. Mutual Exclusion: If process \(P_i\) is executing in its critical section, then no other processes are allowed to execute in their critical sections simultaneously.
  2. 2. Progress: If no process is currently executing in its critical section and there are some processes that wish to enter their critical section, then only those processes that are not executing in their remainder sections can participate in deciding which process will enter next, and this selection cannot be postponed indefinitely. (Prevents deadlock).
  3. 3. Bounded Waiting: There must exist a bound (limit) on the number of times that other processes are allowed to enter their critical sections after a process has made a request to enter and before that request is granted. (Prevents starvation).

1.3 Peterson's Algorithmic Solution (Two-Process Software Synchronization)

Developed by Gary L. Peterson in 1981, this software-based algorithm guarantees all three critical section criteria for two cooperating processes, \(P_0\) and \(P_1\).

Shared Data Structures:

  • int turn; // Indicates whose turn it is to enter the CS.
  • boolean flag[2]; // flag[i] = true indicates process \(P_i\) is ready to enter its CS.
Peterson's Algorithm Structure 
// Structure for Process P_i (where j = 1 - i):
do {
    flag[i] = true;                 // 1. Declare intent: "I want to enter"
    turn = j;                       // 2. Be courteous: "You may go first"
    while (flag[j] && turn == j);    // 3. Busy wait while other process wants in AND it's their turn
    
    /* CRITICAL SECTION */
    
    flag[i] = false;                // 4. Release intent: "I am finished"
    
    /* REMAINDER SECTION */
} while (true);

Rigorous Proof of the Three Conditions:

  1. Mutual Exclusion holds: For both \(P_0\) and \(P_1\) to enter their CS simultaneously, both while loops must evaluate to false at the same time: flag[1] == false || turn == 0 for \(P_0\), and flag[0] == false || turn == 1 for \(P_1\). But both set their flags to true beforehand! Thus, the decision hinges on variable turn. Since turn is a single scalar integer in memory, it can only be 0 or 1, never both. Whichever process set turn last gave priority to the other process and is blocked in the while loop.
  2. Progress holds: A process in the remainder section has flag = false, meaning it never blocks the other process from immediately proceeding.
  3. Bounded Waiting holds: Once \(P_j\) finishes its CS, it resets flag[j] = false. If \(P_j\) immediately tries to re-enter, it sets turn = i, directly handing priority over to waiting process \(P_i\). Thus, \(P_i\) waits at most one critical section entry.

1.4 Hardware Synchronization Primitives: TestAndSet & Swap

Modern multi-core processors provide special atomic machine instructions that execute as a single, uninterruptible clock cycle at the hardware bus level:

1. TestAndSet Instruction (Atomic read-and-set):

boolean TestAndSet(boolean *target) {
    boolean rv = *target;    // Read old value
    *target = true;          // Set target to true
    return rv;               // Return original value
}

Mutual Exclusion with TestAndSet: Shared boolean lock = false.

do {
    while (TestAndSet(&lock));    // Busy wait: loops while lock is true. First process gets false!
    /* CRITICAL SECTION */
    lock = false;                 // Release lock
    /* REMAINDER SECTION */
} while (true);

2. Swap Instruction (Compare-and-Swap / XCHG):

Atomically swaps the contents of two memory words in a single bus lock operation.

1.5 Semaphores: Definition, Wait(), Signal(), and Types

Introduced by Edsger Dijkstra, a Semaphore \(S\) is a synchronization tool represented as an integer variable that, apart from initialization, can only be accessed through two standard atomic operations: wait() (historically termed \(P\) for Dutch proberen - to test) and signal() (historically \(V\) for verhogen - to increment).

Formal Definitions of the Two Atomic Operations:

wait(S) {                          signal(S) {
    while (S <= 0);                    S++;
    S--;                           }
}

Two Types of Semaphores:

  • 1. Counting Semaphore: The integer value can range over an unrestricted domain \((-\infty, +\infty)\). Used to control access to a resource consisting of a finite number of identical instances (e.g., a pool of 5 database connections).
  • 2. Binary Semaphore (Mutex Lock): The integer value can only be 0 or 1. Used to enforce mutual exclusion across a single shared critical section.

Non-Busy Waiting Semaphores (Block & Wakeup Mechanism):

To eliminate wasteful CPU spinning (busy waiting / spinlocks), modern operating systems define semaphores with a process waiting queue:

typedef struct {
    int value;
    struct process *list; // Queue of waiting processes
} semaphore;

void wait(semaphore *S) {
    S->value--;
    if (S->value < 0) {
        add this process to S->list;
        block(); // Transition from RUNNING to WAITING state
    }
}

void signal(semaphore *S) {
    S->value++;
    if (S->value <= 0) {
        remove a process P from S->list;
        wakeup(P); // Transition process P from WAITING to READY state
    }
}

Crucial Exam Insight on Negative Semaphore Values:

When using the non-busy waiting implementation: If \(S.\text{value} < 0\), its magnitude \(|S.\text{value}|\) indicates the exact count of processes currently blocked and suspended in the semaphore's waiting queue!

1.6 Classical Problems of Synchronization (NMIMS PYQ Staples)

1. The Bounded-Buffer (Producer-Consumer) Problem:

A producer process generates data items and puts them into a fixed-capacity buffer of size \(N\). A consumer process takes items out of the buffer one at a time.

  • Shared Semaphores:
    • semaphore mutex = 1; // Guarantees mutual exclusion when accessing buffer array.
    • semaphore empty = N; // Counts empty buffer slots (initially \(N\)).
    • semaphore full = 0; // Counts filled buffer slots (initially 0).
// PRODUCER CODE:                           // CONSUMER CODE:
do {                                       do {
    // produce item in next_produced           wait(full);  // Wait if buffer is empty
    wait(empty); // Wait if buffer full        wait(mutex); // Lock buffer access
    wait(mutex); // Lock buffer access         // remove item from buffer to next_consumed
    // add next_produced to buffer             signal(mutex);
    signal(mutex);                             signal(empty); // Signal slot is free
    signal(full); // Signal item added         // consume next_consumed
} while (true);                            } while (true);

2. The Readers-Writers Problem:

A database is shared among several concurrent processes. Readers only read the database; Writers modify it. Multiple readers can read simultaneously, but a writer requires exclusive access.

  • semaphore rw_mutex = 1; // Mutual exclusion for writers.
  • semaphore mutex = 1; // Protects reader count variable.
  • int read_count = 0; // Number of active readers.
// WRITER PROCESS:                         // READER PROCESS:
do {                                      do {
    wait(rw_mutex);                           wait(mutex);
    /* writing is performed */                read_count++;
    signal(rw_mutex);                         if (read_count == 1)
} while (true);                                   wait(rw_mutex); // First reader locks out writers
                                              signal(mutex);
                                              /* reading is performed */
                                              wait(mutex);
                                              read_count--;
                                              if (read_count == 0)
                                                  signal(rw_mutex); // Last reader releases writers
                                              signal(mutex);
                                          } while (true);

3. The Dining Philosophers Problem:

Five philosophers sit around a circular table. Each spends their life alternating between thinking and eating rice. There are 5 single chopsticks placed between adjacent philosophers. To eat, a philosopher must acquire both their left and right chopsticks.

The Deadlock Hazard: If all 5 philosophers become hungry simultaneously and grab their left chopstick (wait(chopstick[i])), all 5 chopsticks are held! When each attempts to grab their right chopstick, every philosopher blocks indefinitely. The system enters complete Deadlock!

1.7 High-Level Synchronization: Monitors & Condition Variables

While semaphores are powerful, they are error-prone. If a developer accidentally writes signal(mutex) before wait(mutex), mutual exclusion is violated. If they write wait(mutex) twice, the system deadlocks.

Definition: Monitor

A Monitor is a high-level programming language synchronization construct (encapsulated as an abstract data type / class) that guarantees automatic mutual exclusion: only one process can be actively executing inside the monitor at any given time.

To allow processes to wait inside a monitor, condition variables are provided: condition x, y;. Operations on condition variables are strictly: x.wait() (invoking process is suspended until signaled) and x.signal() (resumes exactly one suspended process).

1.8 Message Passing and Precedence Graphs

Message passing coordinates processes through send and receive operations instead of shared variables. Communication may be direct or mailbox-based, and blocking or non-blocking; the chosen semantics determine whether a call waits for its partner or buffer space.

A precedence graph is a directed acyclic graph (DAG) of required ordering constraints. An edge (A ightarrow B) means operation/process (A) must finish before (B) starts. Any topological ordering is a valid execution order; independent nodes may run concurrently. A cycle indicates the stated constraints cannot all be satisfied as a simple precedence order.

For example, if (A ightarrow C) and (B ightarrow C), then (A) and (B) may execute in either order or in parallel, but both must complete before (C).

Problem 3.1: Mathematical Evolution of a Counting Semaphore

Problem Statement (From NMIMS Paper 1): Consider a counting semaphore initialized with a value of \(10\). A series of concurrent processes execute the following operations in sequence:
\(12\text{ Wait}(P)\text{ operations}\) and \(7\text{ Signal}(V)\text{ operations}\).
(a) Compute the resulting value of the semaphore.
(b) State how many processes are blocked in the waiting queue.

GIVEN

Initial value: \(S_0 = 10\)

Total Wait calls: \(W = 12\)

Total Signal calls: \(V = 7\)

FORMULA

Each wait() operation decrements the semaphore value by 1. Each signal() operation increments the semaphore value by 1:

$$S_{\text{final}} = S_0 - W + V$$
CALCULATION
$$S_{\text{final}} = 10 - 12 + 7 = 5$$
FINAL RESULT

\(\text{Final Semaphore Value} = \mathbf{5} \quad | \quad \text{Blocked Processes} = \mathbf{0}\)

Reasonableness Check: Since the final value \(S = 5 > 0\), the resource pool still has 5 available units remaining. Exactly 0 processes are blocked in the waiting queue.

4. Practical Kernel Concurrency

Linux Kernel Primitives
Kernel Architecture Case Study

Spinlocks vs. Mutexes in the Linux Kernel

Within the Linux kernel, engineers choose locking primitives strictly based on execution context:

  • Spinlocks: A process waiting for a spinlock sits in a tight busy-waiting loop checking CPU cache lines. Crucially, interrupt handlers cannot sleep. Therefore, interrupt service routines must exclusively use spinlocks!
  • Mutexes: When a mutex is locked, the calling thread is put to sleep (transitioned to WAITING state) and the CPU is dispatched to another job. Mutexes are used only in user space or process context where sleeping is permitted.
