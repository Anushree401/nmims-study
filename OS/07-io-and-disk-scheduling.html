1. I/O architecture

Devices differ, so controllers and device drivers hide hardware detail behind a uniform OS interface. A device may expose data-in, data-out, status, and control registers; access may use dedicated I/O instructions or memory-mapped I/O. Ports connect devices; buses connect components. Device drivers issue commands and manage device-specific details.

2. Polling, interrupts, and I/O modes

Polling: CPU repeatedly checks a status bit until ready. Simple and sensible for fast completion, but wastes cycles for slow devices. Interrupt-driven I/O: device signals the CPU; handler identifies/serves it, with context/dispatch overhead. Interrupts can be masked/prioritized; exceptions and system-call traps also enter kernel handling. Blocking I/O suspends caller until completion; nonblocking returns available data; asynchronous operation lets work proceed and signals later.

DMA transfers blocks between device and memory with limited CPU involvement; CPU sets up transfer and is notified on completion. (Treat exact transfer modes as illustrated in Unit 6.)

3. Disk scheduling fundamentals

For rotating disks, requests target cylinders; seek movement is commonly approximated by absolute cylinder difference. For path h0→h1→…→hn, total head movement = Σ|hi−hi−1| cylinders. This is movement, not milliseconds: converting to seek time requires a drive model not supplied in the slides.

PolicyOrderTrade-off
FCFSArrival/request orderFair/simple, often large movement.
SSTFNearest request from current head each stepLow local movement, far requests may starve.
SCANMove in one direction servicing requests, reach disk end, reverseElevator; endpoint and direction matter.
C-SCANService in one direction; wrap to opposite end without service on returnMore uniform wait; wrap movement convention must be explicit.
LOOKLike SCAN but reverse at last request in directionAvoids needless trip to physical end.
C-LOOKLike C-SCAN but wrap between furthest requestsSpecify whether wrap counts in movement total.

4. Reliable disk-work procedure

  1. Write request set, initial head, disk bounds, and initial direction.
  2. For FCFS keep listed order; for SSTF recalculate nearest from current head after each selection; resolve equal distances by declared convention.
  3. For sweep policies sort requests around the initial head; follow direction and endpoint/wrap rule exactly.
  4. Show path, then sum adjacent absolute differences. State total in cylinders.

Linux deadline scheduling and other scheduler examples are mentioned in the slides as context; versions/defaults are time-specific and not treated as current facts.

Recap and self-test

Self-test (answers follow)

Why is polling inefficient for a slow device?

CPU busy-waits instead of doing useful work.

How is total disk head movement computed?

Sum absolute cylinder differences between consecutive head positions.

Difference between SCAN and LOOK?

SCAN goes to disk end before reversing; LOOK reverses at the last pending request in that direction.

Does SSTF guarantee no starvation?

No, far requests can be postponed repeatedly.

What must be stated for C-SCAN calculations?

Disk bounds, direction, whether wrap movement counts, and the request service sequence.

5. I/O subsystem and storage details

The kernel I/O subsystem schedules per-device queues, buffers data to bridge speed/size differences, caches copies for faster reuse, and spools output for exclusive devices such as printers. Device reservation gives exclusive access and can contribute to deadlock. Vectored (scatter-gather) I/O combines multiple buffers/operations in one call, reducing calls and copying overhead. DMA moves blocks with less CPU intervention.

Disk access time has seek time (arm movement) plus rotational latency plus transfer time. Rotational latency depends on spindle speed; the slides give no particular drive’s timing model. HDDs use rotating magnetic platters; nonvolatile-memory devices have no moving head and are faster in the described comparison. Low-level formatting creates logical blocks; bad sectors complicate logical-to-physical mapping.

What to know for the exam

Be ready to define the central terms, compare mechanisms using their assumptions and trade-offs, trace a process or algorithm step by step, and justify the result. State units and conventions whenever a question supplies them.
