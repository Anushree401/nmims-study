1. In-Depth Theory & Lecture Explanation

Faithful to UNIT 4.pptx, bankers extended.pptx & NMIMS Past Papers

1.1 Deadlock Definition & System Resource Model

In a multiprogramming system, processes compete for a finite set of resources (e.g., CPU, memory partitions, tape drives, printers, database locks).

Formal Definition of Deadlock

A Deadlock is a situation where a set of processes are blocked because every process in the set holds one or more resources while waiting for another resource that is currently held by another process in that very same set.

$$\forall P_i \in \{P_0, P_1, \dots, P_n\}, \quad P_i \text{ is waiting for a resource held by } P_{(i+1) \bmod (n+1)}$$

Under deadlock, no process can ever execute, complete, or release its resources. The system remains permanently frozen unless an external agent intervenes.

1.2 The Four Coffman Necessary Conditions

In 1971, Edward G. Coffman Jr. proved that a deadlock can arise if and only if all four of the following conditions hold simultaneously in a system:

# Coffman Condition Rigorous Technical Meaning & Hardware Reality
1 Mutual Exclusion At least one resource must be held in a non-shareable mode. Only one process can use the resource at any given time. If another process requests that resource, it must wait until the resource is released.
2 Hold and Wait A process must currently be holding at least one resource and simultaneously waiting to acquire additional resources that are currently being held by other active processes.
3 No Preemption Resources cannot be forcibly taken away from a process holding them. A resource can only be released voluntarily by the holding process after that process has finished its task.
4 Circular Wait A closed circular chain of processes \(\{P_0, P_1, \dots, P_n\}\) must exist such that \(P_0\) is waiting for a resource held by \(P_1\), \(P_1\) is waiting for a resource held by \(P_2\), \(\dots\), and \(P_n\) is waiting for a resource held by \(P_0\).

Exam Golden Rule: All Four Must Hold!

If you can engineer a system to prevent or eliminate even one of these four conditions, a deadlock is mathematically impossible!

1.3 Resource Allocation Graphs (RAG)

A Resource Allocation Graph is a directed graph \(G = (V, E)\) used to precisely model resource allocation and wait states:

  • Vertices (\(V\)): Partitioned into two sets:
    • Processes \(P = \{P_1, P_2, \dots, P_n\}\) (Drawn as circles).
    • Resource Types \(R = \{R_1, R_2, \dots, R_m\}\) (Drawn as squares; internal dots indicate discrete resource instances).
  • Edges (\(E\)): Directed connections:
    • Request Edge (\(P_i \to R_j\)): Directed arrow from process to resource square. Process \(P_i\) is currently waiting for an instance of \(R_j\).
    • Assignment Edge (\(R_j \to P_i\)): Directed arrow originating from an internal instance dot within \(R_j\) to process circle \(P_i\). Resource \(R_j\) is currently allocated to \(P_i\).

Figure 4.1: Resource Allocation Graph showing a complete Deadlock Cycle (\(P_1 \to R_2 \to P_2 \to R_1 \to P_1\)).

Exam Theorem: Cycle vs. Deadlock Relationship:

  • Single-Instance Resource Graphs: A cycle in the graph is a necessary and sufficient condition for deadlock. (If there is a cycle, the system is guaranteed deadlocked!).
  • Multiple-Instance Resource Graphs: A cycle is a necessary condition, but NOT sufficient. A cycle may exist without deadlock if an external process holding an instance of that resource completes and breaks the cycle!

1.4 The Four Strategies for Handling Deadlocks

  1. 1. Deadlock Ignorance (The Ostrich Algorithm): Stick your head in the sand and pretend deadlocks never occur! Used by mainstream OSes (Linux, Windows) because deadlocks are rare in well-designed applications, and the runtime overhead of continuous prevention/avoidance is deemed too high. The burden is pushed onto the application developer.
  2. 2. Deadlock Prevention: Design system protocols that structurally constrain resource requests such that at least one of the four Coffman conditions can never hold.
  3. 3. Deadlock Avoidance (Banker's Algorithm): The OS dynamically tracks resource allocation state and only grants requests if the resulting state is provably Safe.
  4. 4. Deadlock Detection and Recovery: Allow deadlocks to occur freely. Periodically run an algorithm to detect cycles, and invoke recovery (killing processes or preemption).

1.5 Deadlock Prevention: Eliminating Coffman Conditions

Targeted Condition Prevention Protocol & Implementation Strategy Severe Drawback / System Cost
Mutual Exclusion Make all resources shareable (e.g., read-only files, or spooling printers via software daemon). Fundamentally impossible for inherently non-shareable hardware (e.g., tape drives, mutex locks).
Hold and Wait Protocol 1: A process must request and receive all required resources at once before beginning execution.
Protocol 2: A process can only request resources when it currently holds none.		 Severe Resource Underutilization: Resources held but unused for hours sit idle; processes needing many resources face starvation.
No Preemption If process \(P_1\) holding resources requests resource \(R\) that is held by waiting process \(P_2\), \(R\) is preempted from \(P_2\) and given to \(P_1\). If \(R\) is busy with a running process, \(P_1\) is forced to release all its currently held resources! Only practical for resources whose complete machine state can be easily saved and restored (e.g., CPU registers, memory pages). Disastrous for database transactions or disk writes.
Circular Wait Resource Ordering Protocol: Impose a total linear ordering function \(F: R \to \mathbb{N}\) on all resource types (e.g., Tape=1, Disk=2, Printer=3). A process can request a resource \(R_j\) only if \(F(R_j) > F(R_i)\) for all currently held resources \(R_i\). Highly effective (Havender's Method)! However, forces programmers to acquire resources in artificial order, restricting programming flexibility.

1.6 Deadlock Avoidance: Safe States & The Banker's Algorithm

Developed by Edsger Dijkstra, the Banker's Algorithm is designed for systems where resource types have multiple instances. A bank never allocates cash unless it can satisfy the maximum cash needs of every customer in some valid sequence.

Definition: Safe State & Safe Sequence

A system state is Safe if there exists a Safe Sequence \(\langle P_0, P_1, \dots, P_{n-1} \rangle\) of processes such that, for each process \(P_i\), the resources that \(P_i\) can still request can be satisfied by the currently available resources plus the resources already held by all preceding processes \(P_j\) (where \(j < i\)).

Safe \(\implies\) No Deadlock.
Unsafe \(\centernot\implies\) Deadlock (An unsafe state only carries the possibility of deadlock if processes demand their maximum claims simultaneously!).

Data Structures for Banker's Algorithm (System with \(n\) processes and \(m\) resources):

  • Available[m]: Vector of length \(m\). Available[j] = k means \(k\) instances of resource \(R_j\) are free.
  • Max[n][m]: \(n \times m\) matrix. Max[i][j] = k defines the maximum claim of process \(P_i\) for resource \(R_j\).
  • Allocation[n][m]: \(n \times m\) matrix. Number of instances of \(R_j\) currently held by \(P_i\).
  • Need[n][m]: \(n \times m\) matrix. Remaining resources that \(P_i\) may request: $$\mathbf{Need[i][j] = Max[i][j] - Allocation[i][j]}$$

1. The Safety Algorithm:

  1. Let Work = Available (vector of length \(m\)) and Finish[i] = false for \(i = 0, 1, \dots, n-1\).
  2. Find an index \(i\) such that both:
    (a) Finish[i] == false
    (b) Need[i] <= Work
    If no such \(i\) exists, go to Step 4.
  3. Work = Work + Allocation[i]; Finish[i] = true; Go back to Step 2.
  4. If Finish[i] == true for all \(i\), the system is in a Safe State.

2. The Resource-Request Algorithm:

When process \(P_i\) makes a vector request Request[i]:

  1. Check 1: If Request[i] <= Need[i], proceed to Step 2. Else, throw error (process exceeded maximum claim!).
  2. Check 2: If Request[i] <= Available, proceed to Step 3. Else, \(P_i\) must wait (resources not currently free).
  3. Temporary Allocation: The OS pretends to allocate resources by modifying data structures:
    • Available = Available - Request[i];
    • Allocation[i] = Allocation[i] + Request[i];
    • Need[i] = Need[i] - Request[i];
  4. Run the Safety Algorithm on the modified state:
    • If Safe \(\implies\) Grant request immediately!
    • If Unsafe \(\implies\) Roll back state changes; \(P_i\) must wait.

1.7 Deadlock Detection & Recovery

When deadlocks are not prevented or avoided, the OS must periodically execute a detection algorithm. For single-instance resources, this is done by maintaining a Wait-For Graph (collapsing resource nodes into direct process-to-process wait edges) and running cycle detection (\(O(V^2)\)).

Deadlock Recovery Techniques:

  • 1. Process Termination:
    • Abort all deadlocked processes: Guaranteed to break cycle, but discards hours of expensive computation.
    • Abort one process at a time: Abort one, re-run detection. Repeat until cycle breaks. Select victim based on priority, computation completed, and resources held.
  • 2. Resource Preemption:
    • Selecting a Victim: Preempt resources from process with lowest cost.
    • Rollback: Must roll back victim process to a safe checkpoint state.
    • Starvation Prevention: Ensure a process is not perpetually chosen as victim by including rollback count in victim selection cost.

Core 10-Mark Problem

Problem 4.1: Comprehensive Banker's Safety & Safe Sequence Trace

Problem Statement (From NMIMS Paper 5 & Paper 2): Consider a snapshot of a system with 5 processes (\(P_0, P_1, P_2, P_3, P_4\)) and 3 resource types (\(A, B, C\)). Resource type \(A\) has 10 instances, \(B\) has 5 instances, and \(C\) has 7 instances.
Given the snapshot:

ProcessAllocation (\(A, B, C\))Max (\(A, B, C\))Available (\(A, B, C\))
\(P_0\)010753332
\(P_1\)200322
\(P_2\)302902
\(P_3\)211222
\(P_4\)002433

(a) Calculate the Need Matrix.
(b) Determine whether the system is in a Safe State. If yes, find the complete Safe Sequence.

STEP 1: NEED MATRIX

Formula: \(\text{Need}[i] = \text{Max}[i] - \text{Allocation}[i]\)

  • \(\text{Need}(P_0) = (7, 5, 3) - (0, 1, 0) = \mathbf{(7, 4, 3)}\)
  • \(\text{Need}(P_1) = (3, 2, 2) - (2, 0, 0) = \mathbf{(1, 2, 2)}\)
  • \(\text{Need}(P_2) = (9, 0, 2) - (3, 0, 2) = \mathbf{(6, 0, 0)}\)
  • \(\text{Need}(P_3) = (2, 2, 2) - (2, 1, 1) = \mathbf{(0, 1, 1)}\)
  • \(\text{Need}(P_4) = (4, 3, 3) - (0, 0, 2) = \mathbf{(4, 3, 1)}\)
STEP 2: SAFETY ALGORITHM

Initial: \(\text{Work} = \text{Available} = (3, 3, 2)\). All \(\text{Finish} = \text{false}\).

  • Iteration 1:
    • Check \(P_0\): Need \((7, 4, 3) \le (3, 3, 2)\)? False! Cannot satisfy \(P_0\).
    • Check \(P_1\): Need \((1, 2, 2) \le (3, 3, 2)\)? True!
    • \(P_1\) executes and finishes. \(\text{Work} = (3, 3, 2) + \text{Alloc}(P_1)(2, 0, 0) = \mathbf{(5, 3, 2)}\). \(\text{Finish}[P_1] = \text{true}\).
  • Iteration 2: With \(\text{Work} = (5, 3, 2)\):
    • Check \(P_3\): Need \((0, 1, 1) \le (5, 3, 2)\)? True!
    • \(P_3\) executes and finishes. \(\text{Work} = (5, 3, 2) + \text{Alloc}(P_3)(2, 1, 1) = \mathbf{(7, 4, 3)}\). \(\text{Finish}[P_3] = \text{true}\).
  • Iteration 3: With \(\text{Work} = (7, 4, 3)\):
    • Check \(P_4\): Need \((4, 3, 1) \le (7, 4, 3)\)? True!
    • \(P_4\) executes and finishes. \(\text{Work} = (7, 4, 3) + \text{Alloc}(P_4)(0, 0, 2) = \mathbf{(7, 4, 5)}\). \(\text{Finish}[P_4] = \text{true}\).
  • Iteration 4: With \(\text{Work} = (7, 4, 5)\):
    • Check \(P_0\): Need \((7, 4, 3) \le (7, 4, 5)\)? True!
    • \(P_0\) executes and finishes. \(\text{Work} = (7, 4, 5) + \text{Alloc}(P_0)(0, 1, 0) = \mathbf{(7, 5, 5)}\). \(\text{Finish}[P_0] = \text{true}\).
  • Iteration 5: With \(\text{Work} = (7, 5, 5)\):
    • Check \(P_2\): Need \((6, 0, 0) \le (7, 5, 5)\)? True!
    • \(P_2\) executes and finishes. \(\text{Work} = (7, 5, 5) + \text{Alloc}(P_2)(3, 0, 2) = \mathbf{(10, 5, 7)}\). \(\text{Finish}[P_2] = \text{true}\).
FINAL RESULT

The system is in a SAFE STATE.
Valid Safe Sequence: \(\mathbf{\langle P_1, P_3, P_4, P_0, P_2 \rangle}\)

Sanity Check: Final Work vector \((10, 5, 7)\) matches total system resources. All processes terminated successfully!

Resource-Request Trace

Problem 4.2: Evaluating Immediate Grant Request

Problem Statement (From 'bankers extended.pptx' & Exam Papers): Using the system state from Problem 4.1, suppose process \(P_1\) makes an immediate request: $$\text{Request}(P_1) = (1, 0, 2)$$ Can this request be granted immediately?

CHECK 1 & 2
  • Check 1: \(\text{Request} \le \text{Need}\)?
    \((1, 0, 2) \le \text{Need}(P_1)(1, 2, 2)\)? YES! (Process did not exceed maximum claim).
  • Check 2: \(\text{Request} \le \text{Available}\)?
    \((1, 0, 2) \le \text{Available}(3, 3, 2)\)? YES! (Resources are currently free).
TEMP ALLOCATION

Temporarily modify system vectors for \(P_1\):

  • \(\text{Available}_{\text{new}} = (3, 3, 2) - (1, 0, 2) = \mathbf{(2, 3, 0)}\)
  • \(\text{Allocation}(P_1)_{\text{new}} = (2, 0, 0) + (1, 0, 2) = \mathbf{(3, 0, 2)}\)
  • \(\text{Need}(P_1)_{\text{new}} = (1, 2, 2) - (1, 0, 2) = \mathbf{(0, 2, 0)}\)
SAFETY TEST

Run Safety Algorithm with \(\text{Work} = (2, 3, 0)\):

  • Check \(P_1\): \(\text{Need}(P_1) = (0, 2, 0) \le (2, 3, 0)\)? Yes!
    \(P_1\) finishes \(\to \text{Work} = (2, 3, 0) + (3, 0, 2) = \mathbf{(5, 3, 2)}\).
  • With \(\text{Work} = (5, 3, 2)\), sequence \(\langle P_3, P_4, P_0, P_2 \rangle\) satisfies all remaining needs exactly as in Problem 4.1!
CONCLUSION

The resulting state is SAFE (Safe sequence: \(\langle P_1, P_3, P_4, P_0, P_2 \rangle\)).
DECISION: The request by \(P_1\) for \((1, 0, 2)\) can be GRANTED IMMEDIATELY!

3. Comprehensive Comparative Studies

Frequent Exam Distinctions

Table 4.1: Deadlock Prevention vs. Avoidance vs. Detection

Attribute Deadlock Prevention Deadlock Avoidance (Banker's) Deadlock Detection & Recovery
Core Philosophy Strictly eliminate one of the 4 Coffman conditions at design time. Dynamically inspect safe sequences before granting each request. Grant requests freely; detect deadlocks after they occur.
Resource Information Needed None (enforced via rigid access rules or linear orderings). Requires maximum resource claim declarations in advance. Requires current allocation and outstanding wait matrices.
Resource Utilization Low. Severe underutilization due to rigid hold-and-wait restrictions. High. Allocates resources dynamically up to safe limits. Maximum. Zero pre-allocation restrictions.
Runtime Overhead Low. Rules enforced at request time without complex matrix calculations. High. Runs \(O(m \cdot n^2)\) safety algorithm on every request! Moderate. Detection runs periodically (e.g., every 5 minutes).

4. Real-World Deadlock Scenarios

Enterprise Database Systems
Database Deadlocks Case Study

Deadlock Detection in Relational Databases (PostgreSQL / MySQL InnoDB)

Unlike general-purpose operating systems, relational database management systems (RDBMS) actively implement deadlock detection and recovery:

  • Row-Level Locks: Transaction \(T_1\) updates row 100 and requests row 200. Concurrently, transaction \(T_2\) updates row 200 and requests row 100.
  • Wait-For Graph Background Thread: Every 1000 milliseconds, InnoDB checks its internal wait-for graph for directed cycles.
  • Automated Victim Rollback: When a cycle is detected, InnoDB selects the transaction with the fewest modified rows, rolls back its transaction (undoing writes via WAL logs), and releases its locks so the other transaction can finish!

5. Possible University Exam Questions & Marking Guide

NMIMS Pattern: 5 & 10 Mark Solutions
10 Marks

Q1. Explain the four necessary conditions for deadlock occurrence. How can deadlocks be prevented by eliminating circular wait? [From NMIMS Paper 1, 2, 4]

Official Marking Scheme:

  • Explanation of 4 Coffman conditions (Mutual Exclusion, Hold & Wait, No Preemption, Circular Wait): 4 Marks
  • Resource Allocation Graph illustration of conditions: 2 Marks
  • Havender's linear resource ordering protocol to eliminate Circular Wait: 4 Marks

Model Answer Key: Detail the 4 conditions from Section 1.2. Then explain Havender's linear ordering method: assign a unique natural number \(F(R_i)\) to every resource. Enforce that a process holding \(R_i\) can only request \(R_j\) if \(F(R_j) > F(R_i)\). Prove by contradiction: if a circular wait existed (\(P_0 \to P_1 \to \dots \to P_0\)), then \(F(R_0) < F(R_1) < \dots < F(R_0)\), meaning \(F(R_0) < F(R_0)\), which is mathematically impossible!

Q2. Describe the process of deadlock recovery after detection. What are the common methods used? [From NMIMS Paper 5]

Official Marking Scheme:

  • Process termination methods (Abort all vs. Abort one-by-one): 2.5 Marks
  • Resource preemption methods (Victim selection, rollback, starvation prevention): 2.5 Marks

Model Answer Key: Provide the recovery details from Section 1.7. Explain process termination trade-offs and the three critical issues in resource preemption: (1) Selecting the victim with minimum cost, (2) Checkpoint rollback, and (3) Starvation prevention using aging.
