Problem 1.1: Dual Mode Operation, Trap Mechanism & Protection

5 Marks · Paper 4 Q1(a)

What do you mean by Dual-Mode Operation in an Operating System? Explain with a suitable architecture diagram, specify the hardware support required (mode bit), and describe how the CPU switches between User Mode and Kernel Mode during a system call.

CONCEPT

Definition: Dual-mode operation is a fundamental hardware-enforced protection mechanism that separates system execution into at least two distinct operational privilege levels:

1. User Mode (Mode Bit = 1): Executes user applications. Privileged CPU instructions (direct hardware access, disabling interrupts, modifying page tables, halted execution) are strictly prohibited.

2. Kernel Mode / Supervisor Mode / Monitor Mode (Mode Bit = 0): Executes the core operating system kernel with unrestricted, direct access to all hardware devices, CPU registers, and physical memory space.

EXECUTION MECHANISM TRACE

• Triggering Transition (User → Kernel): When a user process requires an OS service (e.g., file read via read()), it executes a software interrupt or TRAP instruction. The hardware automatically changes the Mode Bit from $1 \to 0$ and transfers control to the fixed interrupt vector address in kernel space.

• Kernel Execution: The kernel saves the program counter and CPU state on the kernel stack, validates parameters, looks up the System Call Dispatch Table, and executes the requested privileged operation safely.

• Returning Transition (Kernel → User): Once finished, the kernel executes a privileged Return-from-Interrupt (RTI / IRET) instruction. The hardware resets the Mode Bit from $0 \to 1$, restores the user state, and resumes execution at the instruction following the system call.

FINAL RESULT
Dual-mode operation prevents rogue or crashed user processes from overwriting OS code, monopolizing CPU execution, or directly manipulating physical hardware registers.
NMIMS Exam Trap: Students often forget to explicitly mention the Mode Bit in the CPU Program Status Word (PSW). Without stating that Mode Bit = 1 (User) and Mode Bit = 0 (Kernel), full marks are rarely awarded.

Problem 1.2: Architectural Comparison: Monolithic vs. Layered vs. Microkernel

10 Marks · Paper 5 Q4(A)

Provide a comprehensive comparative analysis of Monolithic, Layered, and Microkernel Operating System architectures across organization, performance, fault isolation, and extensibility.

DETAILED COMPARISON TABLE
Architectural Dimension Monolithic Kernel (e.g., Linux, Traditional Unix) Layered System (e.g., THE Multiprogramming) Microkernel Architecture (e.g., Mach, QNX, Minix)
Core Philosophy All OS services (file system, drivers, memory, scheduler) reside in a single large address space. Hierarchy of concentric layers $M_0 \dots M_N$; each layer only interacts with layer $M-1$ and $M+1$. Strip kernel to minimal essentials (IPC, low-level scheduling, basic memory); all else in user servers.
Execution Privilege Everything executes in Kernel Mode (Ring 0). Lower layers in Kernel Mode; upper layers transition towards User Mode. Only microkernel in Ring 0; File servers, device drivers, and network run in User Mode (Ring 3).
Inter-Module Communication Direct C function calls in shared virtual memory (Fastest). Strictly vertical API calls between adjacent layers. Message Passing (IPC) through microkernel (Incurs context-switching overhead).
Fault Isolation & Reliability Zero isolation: A crash in a 3rd-party printer driver causes a complete Kernel Panic (BSOD). Moderate: Errors can be localized to the specific layer under test. Extreme reliability: Crashed driver/server simply restarts in user space without crashing OS.
Extensibility Difficult; requires kernel re-compilation or dynamic kernel module loading. Challenging; defining strict layer boundaries is mathematically difficult. Very easy; new services added as standard user-space daemon programs.
FINAL RESULT
Monolithic gives raw execution speed; Microkernel gives modular reliability and security; Modern OSs (macOS, Windows NT) employ Hybrid architectures combining both strengths.

Problem 3.1: Debugging Semaphore Inversions in Producer-Consumer

5 Marks · Paper 4 Q1(b)

A student writes the following Producer-Consumer code with semaphores full = 0, empty = N, mutex = 1. Identify the fatal bugs in semaphore usage and provide the corrected implementation:

Producer() { while (true) { produce_item(x); wait(full); // BUG 1 wait(mutex); insert(x); signal(mutex); signal(empty); // BUG 2 } } Consumer() { while (true) { wait(empty); // BUG 3 wait(mutex); remove(x); signal(mutex); signal(full); // BUG 4 consume_item(x); } }
DEFECT ANALYSIS

1. Immediate Deadlock on Start: In the producer, wait(full) is invoked first. Since initially full = 0, the producer immediately blocks itself forever waiting for items that have not yet been produced!

2. Inverted Buffer Semaphores: The producer should wait for empty buffer slots (wait(empty)) and increment full count (signal(full)). Conversely, the consumer must wait for full slots (wait(full)) and increment empty slots (signal(empty)). The student completely swapped the roles of full and empty.

CORRECTED IMPLEMENTATION
semaphore mutex = 1; // Binary semaphore for mutual exclusion semaphore empty = N; // Counting semaphore: starts at buffer capacity N semaphore full = 0; // Counting semaphore: starts at 0 Producer() { while (true) { produce_item(x); wait(empty); // 1. Decrement available empty slots wait(mutex); // 2. Acquire buffer lock insert(x); // Critical Section: Add to shared buffer signal(mutex); // 3. Release buffer lock signal(full); // 4. Increment count of full items } } Consumer() { while (true) { wait(full); // 1. Decrement available full items (blocks if empty) wait(mutex); // 2. Acquire buffer lock remove(x); // Critical Section: Remove from shared buffer signal(mutex); // 3. Release buffer lock signal(empty); // 4. Increment count of empty slots consume_item(x); } }
Rule of Thumb: Counting semaphores (empty and full) must ALWAYS wrap around the binary mutex lock. Putting wait(mutex) outside wait(empty) can cause a deadly embrace deadlock!

Problem 3.2: Peterson's Algorithm Formal Verification

5 Marks · Paper 5 Q1(B)

Analyze Peterson's Algorithm for two processes $P_i$ and $P_j$. State whether it satisfies the three critical section requirements: (1) Mutual Exclusion, (2) Progress, and (3) Bounded Waiting. Justify each mathematically.

MATHEMATICAL VERIFICATION

1. Mutual Exclusion is Preserved: Process $P_i$ can enter its critical section if and only if flag[j] == false OR turn == i. Suppose for contradiction that both $P_i$ and $P_j$ are inside the critical section simultaneously. This requires both flag[i] == true and flag[j] == true. However, the variable turn can hold only one value at any moment: either $i$ or $j$. If turn == i, $P_j$ was forced to spin in its while loop; if turn == j, $P_i$ was forced to spin. Contradiction!

2. Progress Requirement is Satisfied: If $P_j$ is in its remainder section, flag[j] == false. When $P_i$ sets flag[i] = true and turn = j, the condition (flag[j] && turn == j) evaluates to false immediately. $P_i$ enters its critical section without delay.

3. Bounded Waiting is Met: When $P_i$ finishes its critical section, it resets flag[i] = false, releasing $P_j$. If $P_i$ wishes to re-enter, it must set turn = j, yielding the next entry to $P_j$. Thus, $P_j$ enters after at most one execution of $P_i$.

FINAL RESULT
Peterson's algorithm is mathematically proven to guarantee Mutual Exclusion, Progress, and Bounded Waiting for 2 concurrent processes.

$$\text{New Work} = (5, 3, 2) + (2, 1, 1) = \mathbf{(7, 4, 3)}, \quad \text{Finish}[P4] = \text{True}$$

• P3 and P5 can easily finish next!

Problem 4.2: Resource Allocation Graph (RAG) Deadlock Analysis

10 Marks · Paper 4 Q7(a)

Consider 3 processes ($P_1, P_2, P_3$) and 2 resource types: $R_1$ (1 instance) and $R_2$ (2 instances). Allocation and Request tables are given below:

ProcessAllocationRequest
R1R2R1R2
P11001
P20110
P30100

Draw the Resource Allocation Graph. Is the system deadlocked? If not, find the execution sequence. If deadlocked, identify which process termination resolves the deadlock.

RAG TOPOLOGY & CYCLE DETECTION

Graph Edges:

• Assignment Edges (Allocation): $R_1 \to P_1$, $R_2 \to P_2$, $R_2 \to P_3$.

• Request Edges: $P_1 \to R_2$, $P_2 \to R_1$.

• Total instances: $R_1 = 1$, $R_2 = 2$.

• Available resources: $R_1 = 1 - 1 = 0$, $R_2 = 2 - (1 + 1) = 0$.

Cycle Analysis:

There exists a directed cycle: $P_1 \to R_2 \to P_2 \to R_1 \to P_1$.

However, $R_2$ has multiple instances (2 instances)! One instance of $R_2$ is allocated to $P_3$, and $P_3$ has zero outstanding requests!

GRAPH REDUCTION TRACE

• Step 1: Process $P_3$ is not waiting for any resource ($\text{Request} = (0, 0)$). $P_3$ can finish its execution safely and releases its instance of $R_2$.

$\text{Available } R_2 \text{ becomes } 0 + 1 = \mathbf{1}$.

• Step 2: Process $P_1$ requests 1 instance of $R_2$. Since 1 instance of $R_2$ is now available, $P_1$'s request is satisfied! $P_1$ finishes and releases both its held resources: $R_1$ (1 instance) and $R_2$ (1 instance).

$\text{Available } R_1 \text{ becomes } \mathbf{1}, \quad R_2 \text{ becomes } \mathbf{1}$.

• Step 3: Process $P_2$ requests 1 instance of $R_1$. Since $R_1$ is now free, $P_2$'s request is satisfied. $P_2$ finishes!

FINAL RESULT
Verdict: THERE IS NO DEADLOCK.
Although a cycle exists ($P_1 \to R_2 \to P_2 \to R_1 \to P_1$), deadlock does NOT occur because $R_2$ is a multi-instance resource, and unblocked process $P_3$ releases an instance that breaks the cycle.
Valid Execution Sequence: $\mathbf{\langle P_3, P_1, P_2 \rangle}$.
NMIMS Exam Trap: A common exam mistake is assuming that "Cycle in RAG = Deadlock". In multi-instance resource graphs, a cycle is a necessary but NOT a sufficient condition for deadlock!

Problem 5.1: Partition Allocation Simulation (First-Fit, Best-Fit, Worst-Fit)

10 Marks · Paper 4 Q5(b)

Consider five memory partitions of sizes 350 KB, 700 KB, 580 KB, 450 KB, and 300 KB in the given order. Apply First-Fit, Best-Fit, and Worst-Fit algorithms to place processes of sizes 360 KB, 600 KB, 425 KB, and 250 KB (in order). For each algorithm, show process placement and state which processes must wait.

1. FIRST-FIT SIMULATION

Allocate each process to the first available hole that is large enough:

• Process 1 (360 KB): Skips 350 KB (too small) → Placed in 700 KB partition. Remaining hole $= 700 - 360 = 340\text{ KB}$.

• Process 2 (600 KB): Skips 350 KB, skips 340 KB → Skips 580 KB (too small) → Skips 450 KB → Skips 300 KB → CANNOT BE ALLOCATED (MUST WAIT!).

• Process 3 (425 KB): Skips 350 KB, skips 340 KB → Placed in 580 KB partition. Remaining hole $= 580 - 425 = 155\text{ KB}$.

• Process 4 (250 KB): Placed in the very first partition: 350 KB partition. Remaining hole $= 350 - 250 = 100\text{ KB}$.

First-Fit Result: P1 in 700 KB, P3 in 580 KB, P4 in 350 KB. P2 (600 KB) must wait.

2. BEST-FIT SIMULATION

Allocate each process to the smallest hole that is large enough (minimizes leftover fragment):

• Process 1 (360 KB): Candidates $\ge 360$: {700, 580, 450}. Smallest is 450 KB! Placed in 450 KB partition. Remaining hole $= 450 - 360 = 25\text{ KB}$.

• Process 2 (600 KB): Candidates $\ge 600$: {700}. Placed in 700 KB partition. Remaining hole $= 700 - 600 = 100\text{ KB}$.

• Process 3 (425 KB): Candidates $\ge 425$: {580}. Placed in 580 KB partition. Remaining hole $= 580 - 425 = 155\text{ KB}$.

• Process 4 (250 KB): Candidates $\ge 250$: {350, 300}. Smallest is 300 KB! Placed in 300 KB partition. Remaining hole $= 300 - 250 = 50\text{ KB}$.

Best-Fit Result: ALL FOUR PROCESSES ALLOCATED SUCCESSFULLY! (P1 → 450 KB, P2 → 700 KB, P3 → 580 KB, P4 → 300 KB).

3. WORST-FIT SIMULATION

Allocate each process to the largest available hole (leaves largest remaining fragment):

• Process 1 (360 KB): Largest available hole is 700 KB. Placed in 700 KB. Remaining hole $= 700 - 360 = 340\text{ KB}$.

Available partitions now: {350, 340, 580, 450, 300}.

• Process 2 (600 KB): Largest available hole is 580 KB. Since $600 > 580$, P2 CANNOT BE ALLOCATED (MUST WAIT!).

• Process 3 (425 KB): Largest available hole is 580 KB. Placed in 580 KB. Remaining hole $= 580 - 425 = 155\text{ KB}$.

Available partitions now: {350, 340, 155, 450, 300}.

• Process 4 (250 KB): Largest available hole is 450 KB. Placed in 450 KB. Remaining hole $= 450 - 250 = 200\text{ KB}$.

Worst-Fit Result: P1 in 700 KB, P3 in 580 KB, P4 in 450 KB. P2 (600 KB) must wait.

FINAL RESULT
Best-Fit performs best because it allocates all 4 processes without any process waiting.
Both First-Fit and Worst-Fit fail to allocate Process 2 (600 KB) because Process 1 prematurely consumed the 700 KB partition!

2. LRU SIMULATION (Least Recently Used)

Page that has not been referenced for the longest time is replaced:

• Initial 4 references: 2, 3, 4, 5 (4 faults) → Memory: $[2, 3, 4, 5]$.

• Next references: 3 (Hit), 2 (Hit) → Recency order (most to least): $2, 3, 5, 4$.

• 6: Fault! Least recently used is 4. Replace 4 → Memory: $[2, 3, 6, 5]$.

• 7: Fault! LRU is 5. Replace 5 → Memory: $[2, 3, 6, 7]$.

• 3: Hit! • 2: Hit! • 3: Hit! Memory remains $[2, 3, 6, 7]$.

• 4: Fault! LRU is 6. Replace 6 → Memory: $[2, 3, 4, 7]$.

• 3: Hit! • 4: Hit! • 7: Hit!

3. OPTIMAL SIMULATION (Bélády's Min)

Replaces the page that will not be used for the longest period of time in the future:

• First 4 requests: 2, 3, 4, 5 (4 faults). Next: 3 (Hit), 2 (Hit).

• 6: Looking forward: 7, 3, 2, 3, 4, 8... Page 5 is never referenced again! Replace 5 with 6 → $[2, 3, 4, 6]$.

• 7: Looking forward: 3, 2, 3, 4, 8... Page 6 is never referenced again! Replace 6 with 7 → $[2, 3, 4, 7]$.

• Now memory holds $[2, 3, 4, 7]$.

Look at subsequent references: 3 (Hit), 2 (Hit), 3 (Hit), 4 (Hit)!

• 8: Fault! Future references from pos 13: 7, 4, 3, 2, 3, 4, 7. Page 2 is referenced latest (at pos 17). Replace 2 with 8 → $[8, 3, 4, 7]$.

• 2: Fault! Future references: 3, 4, 7. Page 8 is never used again! Replace 8 with 2 → $[2, 3, 4, 7]$.

• References: 3 (Hit), 4 (Hit), 7 (Hit)!

Problem 7.1: Disk Scheduling Cylinder Trace (FCFS vs. SCAN vs. C-SCAN)

10 Marks · Paper 4 Q4(b)

A disk queue has cylinder requests: 2069, 1212, 2296, 2800, 544, 1618, 356, 1523. Head start position is at cylinder 2150. Cylinders are numbered 0 to 4999. Calculate total head movement (in cylinders) for:
I. FCFS (First-Come-First-Served)
II. SCAN (Elevator), assuming head is initially moving towards 4999.
III. C-SCAN (Circular SCAN), assuming head is initially moving towards 4999.
Compare the algorithms based on total head movement.

1. FCFS HEAD MOVEMENT

Service requests strictly in queue arrival order:

$$\text{Path: } 2150 \to 2069 \to 1212 \to 2296 \to 2800 \to 544 \to 1618 \to 356 \to 1523$$

• $|2150 - 2069| = 81$

• $|2069 - 1212| = 857$

• $|1212 - 2296| = 1084$

• $|2296 - 2800| = 504$

• $|2800 - 544| = 2256$

• $|544 - 1618| = 1074$

• $|1618 - 356| = 1262$

• $|356 - 1523| = 1167$

$\text{Total FCFS Movement} = 81 + 857 + 1084 + 504 + 2256 + 1074 + 1262 + 1167 = \mathbf{8285\text{ cylinders}}$.

2. SCAN (ELEVATOR) ALGORITHM

Head moves towards 4999, services all requests in its path, touches boundary 4999, reverses, and services remaining requests in downward direction.

Sorted Requests: $\{356, 544, 1212, 1523, 1618, 2069\} \leftarrow [2150] \rightarrow \{2296, 2800\}$.

1. Upward Path: $2150 \to 2296 \to 2800 \to 4999$ (End of disk).

$$\text{Upward Movement} = 4999 - 2150 = 2849\text{ cylinders}$$

2. Downward Path: $4999 \to 2069 \to 1618 \to 1523 \to 1212 \to 544 \to 356$.

$$\text{Downward Movement} = 4999 - 356 = 4643\text{ cylinders}$$

$\text{Total SCAN Movement} = 2849 + 4643 = \mathbf{7492\text{ cylinders}}$.

3. C-SCAN (CIRCULAR SCAN) ALGORITHM

Head moves towards 4999, services requests, touches 4999, jumps directly to cylinder 0 without servicing, and continues moving in the original upward direction.

1. Upward Leg: $2150 \to 2296 \to 2800 \to 4999$. Movement $= 4999 - 2150 = 2849$.

2. Return Jump: $4999 \to 0$. Movement $= 4999 - 0 = 4999$.

3. Second Leg from 0: $0 \to 356 \to 544 \to 1212 \to 1523 \to 1618 \to 2069$. Movement $= 2069 - 0 = 2069$.

$\text{Total C-SCAN Movement} = 2849 + 4999 + 2069 = \mathbf{9917\text{ cylinders}}$.

(Note: In standard NMIMS marking, if return jump $4999 \to 0$ is excluded as pure seek latency, movement is $2849 + 2069 = 4918$).

FINAL RESULT
• FCFS Movement: $8285\text{ cylinders}$
• SCAN Movement: $7492\text{ cylinders}$ (Lowest head movement)
• C-SCAN Movement: $9917\text{ cylinders}$ (Provides more uniform wait time at the cost of the circular jump).
NMIMS Exam Trap: In SCAN, the head MUST travel all the way to the boundary cylinder ($4999$) before reversing! In LOOK and C-LOOK, the head reverses immediately at the furthest pending request ($2800$).

Problem 8.1: Process Control Block (PCB) Structure & Context Switching Overhead

5 Marks · Paper 4 Q7(b)

Define a Process Control Block (PCB). Enumerate its key structural fields. Explain with a timing sequence diagram how the PCB enables preemptive multitasking, and define the concept of context switching overhead.

PCB ARCHITECTURE

The PCB is the kernel data structure representing an execution instance of a program:

• Process Identifier (PID): Unique integer identifying the process.

• Process State: New, Ready, Running, Waiting, or Terminated.

• Program Counter (PC): Memory address of the next instruction to execute.

• CPU Registers: Accumulators, index registers, stack pointers, general-purpose registers.

• CPU-Scheduling Info: Process priority, scheduling queue pointers.

• Memory-Management Info: Value of base/limit registers, or page/segment tables.

• Accounting & I/O Status: CPU time used, time limits, list of open file descriptors.

CONTEXT SWITCH MECHANISM

1. Interrupt or system call occurs while Process $P_0$ is running.

2. Hardware saves current PC and processor status words.

3. Kernel saves all architectural registers into $P_0$'s PCB ($\text{PCB}_0$).

4. Scheduler selects Process $P_1$ from the ready queue.

5. Kernel restores registers and CPU state from $P_1$'s PCB ($\text{PCB}_1$).

6. CPU updates Memory Management Unit (flushes or tags TLB entries).

7. RTI instruction transfers control to $P_1$.

Context Switching Overhead: During a context switch, the CPU performs pure administrative bookkeeping. No useful application computation is performed. It represents pure overhead ($1 \dots 10\mu s$), which limits how small scheduling time slices can be set.

FINAL RESULT
Without the PCB, an operating system could not save process state to resume execution transparently, making time-shared multitasking impossible.

Problem 8.2: File Allocation Strategies: Contiguous vs. Linked vs. Indexed (Inodes)

8 Marks · Standard Form

Compare Contiguous, Linked, and Indexed (Unix Inode) file allocation methods with respect to random access speed, external fragmentation, file growth flexibility, and storage reliability.

COMPARATIVE ANALYSIS
Metric / Feature Contiguous Allocation Linked Allocation Indexed Allocation (e.g., Unix Inode)
Disk Block Layout Consecutive linear blocks on disk ($B, B+1, \dots, B+k-1$). Scattered blocks; each block contains data + pointer to next block. Each file has an index block (or Inode) holding direct pointers to data blocks.
Sequential Access Extremely fast (minimum seek distance). Fast. Fast.
Direct / Random Access Instant: $i$-th block address is simply $B + i$. Terrible: Must traverse through $i$ disk blocks sequentially. Fast: Direct index lookup in memory table ($O(1)$).
External Fragmentation Severe (requires periodic disk defragmentation). Zero: Any free block on disk can be chained. Zero: Any free block can be indexed.
File Growth Very difficult (file cannot expand if adjacent block is occupied). Seamless: Append newly allocated block to tail. Seamless: Add pointer to index block (or multi-level indirect blocks).
Fault Reliability Good. Poor: A single corrupt pointer breaks the entire rest of the file! Very good; pointer corruption isolated to specific files.
FINAL RESULT
Modern file systems (ext4, NTFS) use indexed extent-based structures: contiguous extents for high I/O throughput, with multi-level indirect index pointers to accommodate files of multi-terabyte size.
